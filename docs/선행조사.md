# 선행조사 — 토큰 최소화 모델기반 자율(MBA): LLM 은 컴파일러로만

조사 2026-10-01, 하위 에이전트 한 번(웹 검색 25 질의 + 원문 열기 시도). **코드보다 먼저** 커밋되는 문서다.
묻는 것은 하나다: *자연어를 LLM 이 한 번만 기호 임무/IR 로 컴파일하고, 그 뒤 정상 운용은 토큰 0 으로
`policy[state][event]` 표 · 이벤트 구동 FSM/BT · 의존 원뿔만 깨우는 증분 모델기반 진단 · 우선순위 중재 ·
모델 조각 검색으로 돌리며, 이 전체를 작은 DSL 에서 C/C++ 로 내리는 것* 이 이미 있나.

**읽기 수준을 먼저 밝힌다.** 프록시가 거의 다 막았다. 직접 시도해서 EGRESS_BLOCKED / 접속 거부를 확인한 곳:
`arxiv.org`(abs) · `ar5iv.labs.arxiv.org` · `ai.jpl.nasa.gov` · `mers-papers.csail.mit.edu` · `groups.csail.mit.edu` ·
`aaai.org` · `cdn.aaai.org` · `ijcai.org` · `jair.org` · `mlanthology.org` · `ntrs.nasa.gov` · `academia.edu` ·
`openreview.net` · `proceedings.mlr.press` · `scholar.google.com` · `en.wikipedia.org` · `pith.science` ·
`lacuna.tiptreesystems.com` · `typefly.github.io`. **열린 곳은 `github.com` 저장소 페이지뿐**이었다.
그래서 **논문은 전문도 초록 페이지도 하나도 못 읽었다 — 아래 논문 인용은 전부 [출처:조각]**(검색 결과 요약에서

## 가장 가까운 선행연구

**하나로 고르면: Titan / RMPL — 반응형 모델기반 프로그래밍** (Williams · Ingham 외, "Model-based programming of
intelligent embedded systems and robotic space explorers", Proc. IEEE 2003; "A Reactive Model-based Programming Language
for Robotic Space Explorers", i-SAIRAS 2001) [출처:조각]

- 무엇: 프로그래머가 RMPL(동기·반응형 언어 + 숨은 상태 변수 읽기/쓰기)로 *원하는 상태* 를 쓰면, 실행기 Titan 이
  부품 단위 선언형 모델로 **모드 추정(진단)** 과 **모드 재구성(반응형 계획)** 을 빠른 sense-decide-act 고리 안에서
  한다. "propositional inference 로 현재·원하는 상태를 연역, model-based reactive planning 으로 옮긴다" [출처:조각].
- 왜 가장 가깝나: 우리 그림의 [2] 기호표 → [3] 실행기 → [4][5] 신념·고장 모델 → [6][7] 정책·행동 이 **통째로 이
  계보다.** 우리 설계 문서가 스스로 "Remote Agent / Livingstone 의 추론을 유지" 라고 쓰는 그 자리이며, Remote Agent
  이후 MIT MERS 가 그것을 *언어(RMPL) 하나 + 컴파일된 실행기* 로 정리한 것이 Titan 이다. 우리 [4]의 "DSL 하나:
  Model→State→Event→Policy→Action" 은 RMPL 이 이미 한 일의 이름을 바꾼 것일 가능성이 높다.

**토큰-0 핵심부(컴파일)만 보면 더 가까운 것: MEXEC** (Barrett, "Model Compilation for Real-Time Planning and Diagnosis
with Feedback", IJCAI 2005, JPL) [출처:조각] — 되먹임 있는 장치 모델을 **오프라인에서 구조로 컴파일**하고, 온라인에서는
n 개 센서 측정으로 가장 그럴듯한 현재 모드와, 목표 모드에 이를 가장 그럴듯한 n−1 걸음 재구성 계획을 계산한다.
"모델기반의 장점 + 지식 컴파일로 규칙기반 수준의 실시간 성능" 이 요약의 취지다. 우리의 "Livingstone → 증분 진단,
제약추론 → 비트마스크/표 조회" 는 이 논문이 정면으로 다룬 자리다. 그 앞에 **Burton** (Williams · Nayak 1997, DS1 의
재구성 계획기) 이 "모델 컴파일 · 인과 분석 · 온라인 정책 구성으로 평균 상수 시간에 제어 행동 하나" 를 냈다 [출처:조각]
— 이것이 사실상 `policy[state][goal]` 의 원형이다.

**토큰 경제 쪽 틀로는: Neuro-Symbolic Computer Use** (arXiv:2609.36927, 2026) [출처:조각] — 반복 작업을 매번 에이전트가
다시 계획하지 않고 **학습된 실행 코드 정책** 으로 돌리며, 관측 의존 결정만 신경망에 맡기고 상태변경 걸음마다 사전 검증기를
둔다. 요약 수치: 실행당 비용 15–217× ↓, 지연 3.4–5.1× ↓, Pass^3 +3.6–15.8. "LLM 을 정상 경로에서 빼고 코드가 1차,
에이전트가 비싼 대체" 라는 우리 주장의 *동기와 측정 방식* 이 이미 여기 있다(영역은 컴퓨터 사용, 모델기반 진단 없음).

## 우리가 다른 점 — 주장이 아니라 후보로

솔직하게: **토큰-0 핵심부의 구성요소 하나하나에는 방법상 새것이 보이지 않는다.** 표 정책(Burton) · 컴파일된 진단(MEXEC ·
d-DNNF · 시간 결정나무) · 증분/초점 진단(GDE · Sherlock · CDA*) · 우선순위 중재(subsumption) · 언어+실행기(RMPL/Titan) ·
NL→형식 IR(LLM+P · NL2LTL · BTGenBot) 가 다 있다. 남는 것은 조합과 측정이다.

1. **LLM 을 RMPL/Livingstone 계열 *컴파일된 모델기반 실행기* 의 자연어 앞단 컴파일러로 쓰는 조합.** NL→IR 계보는 IR 의
   소비자가 PDDL 계획기 · LTL/STL 합성기 · BT 실행기이고, **모드 추정 + 고장 재구성을 하는 모델기반 실행기** 를 소비자로
   둔 것은 이번 조사에서 못 찾았다(RMPL/Livingstone + LLM 질의 2회, 둘 다 무관한 결과). 단 MERS 논문 목록 · DX 학회록을
   **못 열었으므로** 이것은 결과가 아니다.
2. **토큰 예산을 1차 측정량으로 둔 것.** "정상 운용 토큰 ≈ 0, 토큰 경계는 NL 파싱 · 미지 상황 · 임무 재구성 셋뿐" 을
   *잰다*. TypeFly 는 응답 지연·토큰 효율을, Neuro-Symbolic Computer Use 는 실행당 비용을 이미 잰다 — 차이는 고장·진단이
   있는 자율 고리에서 "토큰이 새는 경로가 셋뿐임" 을 보이는 것뿐이다. 이 차이는 **측정 설계의 차이**이지 방법이 아니다.
3. **UNKNOWN → 안전 대체 → 관측 → 신념 갱신 → 알려진 상태** 로 *미지 상황에서도 LLM 을 안 부르는* 경로. 이것은 Remote
   Agent 의 안전 모드 · Livingstone 의 "unknown 고장 모드" 와 같은 발상일 공산이 크다([출처:기억]: Livingstone 모델에는
   확률 낮은 unknown 모드가 있다 — 미확인).
4. **"문서 RAG" 대신 상태 ID 로 모델 조각을 꺼내는 것.** 이것은 Sherlock/GDE 의 초점 · 의존 원뿔과 같은 것을 LLM 시대
   용어로 다시 쓴 것일 수 있다. 우리 쪽 새 점이 있다면 *LLM 이 오프라인으로 지은 조각* 을 그렇게 색인한다는 것인데,
   그건 DX 2024/2025 의 "LLM 으로 진단 모델 짓기" 와 겹친다.

**1 만이 그나마 '연결' 의 차이**이고 2–4 는 측정·용어의 차이다. 가장 좁게 말하면 남는 후보는 이것 하나다:
*"RMPL/Livingstone 형 컴파일 실행기의 자연어 앞단을 LLM 컴파일러로 두고, 정상 운용 토큰 0 과 토큰 경계 셋을 잰 것."*

## 새롭지 않게 만들 가능성

- **MIT MERS 가 이미 했을 가능성.** Williams 연구실은 Kirk · Enterprise · pTulip 등으로 계보를 이어 왔고, 2023 이후
  LLM 앞단을 붙인 논문이 있을 법하다. 이 연구실 출판 목록을 못 열었다 — **가장 먼저 지워야 할 가능성.**
- **NASA/JPL 쪽** (PLEXIL · MEXEC 후속 · Europa Lander 자율 · ROSA) 이 LLM 을 명령 작성/번역기로 쓰고 실행은 기존
  실행기에 맡기는 연구 — ntrs.nasa.gov 를 못 열었다.
- **DX 워크숍 (Principles of Diagnosis) 2023–2026** 에 "LLM + 컴파일된 진단" 이 있을 가능성. DX 2024/2025 제목 둘만 봤다.
- **BT 계열이 이미 같은 주장을 함.** BTGenBot 은 README 상 "LLM 은 생성 단계에서만, 실행은 정적 XML" 이다. 거기에
  BT 의 조건 노드로 고장 감시를 붙이면 우리 그림과 구분이 흐려진다. 차이는 *모델기반 진단* 하나다.
- **일반화 계획(Silver 외)** 이 "도메인당 한 번 합성, 이후 LLM 0" 을 이미 보였다. 우리 "한 번 컴파일" 의 토큰 논리는
  거기 포함된다.
- **산업계 관행.** "LLM 은 자연어 → 설정/DSL, 실행은 결정론적 제어기" 는 드론·PLC·로봇 업계에서 흔한 설계일 수 있고,
  논문 없이 제품으로만 있을 수 있다(검색 안 함).
- **토큰 측정이 시시할 가능성.** 정상 운용에서 LLM 을 안 부르니 토큰이 0 인 것은 *정의상* 0 이다. 측정으로 의미를 가지려면
  같은 임무를 LLM-in-the-loop(LLMSat 류) · 이벤트 구동 재계획(CoMuRoS 류) 기준선과 성공률을 맞춘 채 비교해야 하고, 그렇지
  않으면 "토큰 0" 은 발견이 아니다(CLAUDE.md "사소한 설명부터 죽인다").

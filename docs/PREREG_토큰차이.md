# 사전등록 — 토큰 차이 실측 (V1)

**수를 보기 전에 커밋한다.** 하니스: `bench/token_ab.py`. 원자료: `bench/results/<실행ID>/runs.jsonl`.

## 물음

같은 과제를 (a) LLM 이 루프를 도는 방식과 (b) MBA(LLM 은 관문을 지난 컴파일 한 번, 나머지는 토큰 0 실행)로
돌렸을 때, **과제당 LLM 토큰(실패 포함)** 이 얼마나 다른가. 성공은 나빠지지 않는가.

## 0단계 — 계기부터 (이것이 서야 비교를 말한다)

모든 `claude -p` 호출마다 토큰을 **두 길** 로 센다.
1. 결과 JSON 의 `usage`(입력 · 캐시 만들기 · 캐시 읽기 · 출력)
2. 그 세션의 추적 파일(`~/.claude/projects/**/<session_id>.jsonl`)의 assistant 줄 usage 합(같은 message id 는 마지막 줄 하나)

**규칙:** 호출마다 네 종류 합의 차가 5% 이하. 하나라도 넘으면 비교를 보고하지 않고 그 까닭부터 적는다.
추가로 추적에 `Stop hook feedback` 이 있으면 적는다(이 컨테이너의 stop 훅이 턴을 늘렸는지).

## 팔

| 팔 | 무엇 |
|---|---|
| **LOOP** | `claude -p` 가 기본 도구(Bash 등)로 과제를 끝까지 한다. 기준선 |
| **TOOL** | LOOP + walp MCP 도구(`walp_wait` · `walp_publish`). "사건 때만 LLM" 에 가장 가까운 강한 기준선. T1 · T2 만 |
| **MBA** | 결정적 파서 → (못 하면) 관문 → `claude -p` 컴파일 **한 번**(LOOP 와 같은 깃발) → 닫힌 연산 집합을 토큰 0 으로 실행. 같은 질문 · 같은 상태는 캐시 |
| **MBA-bare** | MBA 와 같되 컴파일 호출에 `--tools ""`. 고정 머리(P) 몫을 따로 보려고 |

모두 `--model claude-haiku-4-5-20251001`, `--strict-mcp-config`(TOOL 은 walp 만), 권한 우회, 새 임시 디렉터리.

## 관문 설정 (이 실험의 값 — D-R1 이 정해지기 전 임시)

컴파일 · 의도 자리의 사전 (9, 1) → p = 0.9 > θ 0.8. 그래서 관문은 이 실험에서 늘 부른다. **관문의 거절 효과는 이 실험이 재지 않는다.**

## 사소한 설명 — 재서 죽일 것

1. **MBA 가 0 인 것은 LLM 이 필요 없는 과제라서** — T4 는 정의상 그렇다(어휘 안). T4 는 "결정적 파서의 몫" 으로만 읽는다
2. **줄어든 것이 호출 수(N)가 아니라 머리(P)** — 호출당 토큰과 호출 수를 따로 적고, MBA 와 MBA-bare 를 맞댄다
3. **캐시 순서** — 캐시 만들기 · 읽기를 따로 적는다. 팔 순서를 돌린다
4. **LOOP 가 실패해 재시도로 부풀었다** — 성공 수와 턴 수를 같이 적는다
5. **MBA 는 닫힌 연산 집합 밖의 과제를 못 한다** — 이 과제들은 그 집합 안에서 골랐다. 일반 에이전트 대비 주장이 아니다

## 무효화

- 0단계 계기 대조가 5% 를 넘으면 전부
- MBA 의 성공이 LOOP 보다 적은 과제는 그 과제의 차이를 주장하지 않는다
- 차이가 런 간 범위 안이면 "차이 없음"

4. **(파일럿 3)** T3 는 MBA · BARE 모두 섰다(첫 질문 컴파일 1 회, 두 번째는 캐시). T5 BARE 가 실패했다 -- 임무 과제에도 연산

### 나눠 읽기 — 줄어든 것은 어디서 왔나 (사소한 설명 2)
- **호출 수(N) 몫 = MBA 대 LOOP**(같은 기본 머리): T1 0.49 · T2 0.47 · T3 0.27 · T5 1.01. LOOP 는 한 과제에 2~6 턴,
  MBA 는 컴파일 1 턴이다. T5 는 둘 다 1 호출이라 차이가 없다(예상대로).
- **고정 머리(P) 몫 = BARE 대 MBA**: 호출 하나가 ~29k 에서 ~1.2~1.9k 로(약 1/20). MBA 호출 29k 중 캐시 읽기 24.2k ·
  캐시 만들기 4.3k 가 머리다. **이 측정에서 가장 큰 지렛대는 N 이 아니라 P 였다.**
- 토큰 종류: LOOP 의 대부분은 캐시 읽기(T2 121.6k / 129.1k). BARE 는 캐시를 안 쓰고 새 입력 ~1.1k + 출력.

### 사전등록 규칙대로 판정
- **T1 · T3**: MBA 와 LOOP 의 범위가 겹치지 않는다(T1 28.9~29.0k vs 58.3~59.3k, T3 28.7~28.8k vs 86.1~115.6k), 성공은 MBA ≥ LOOP → **차이 있음**
- **T2**: 평균은 0.47 이지만 **범위가 겹친다**(MBA 28.9~122.3k vs LOOP 89.0~149.4k) → 규칙상 **"차이 없음"**. 겹침은 MBA 의
  실패 1 회(아래) 때문이다
- **T4**: MBA 0 은 정의상(어휘 안 — 결정적 파서의 몫). 사소한 설명 1 그대로다. 발견으로 세지 않는다
- **T5**: 차이 없음(1.01)
- **BARE**: 모든 과제에서 범위가 겹치지 않고 성공 3/3 → **차이 있음**(LOOP 의 1.2~5.1%)

### 실패와 그 까닭 (추적에서 직접 봄)
- **LOOP T1 2 회 · TOOL T1 1 회**: `wait <PID>` 를 남의 프로세스에 걸었다 -- 곧바로 돌아와 `step2` 를 답했다(기다리지 않음)
- **LOOP T2 1 회 · TOOL T2 1 회**: 밀기 전에 "푸시하시겠습니까?" 로 멈췄다
- **TOOL T2 1 회**: 밀었지만 커밋 메시지가 한 줄에 `Co-Authored-By … Claude-Session: <이 세션 링크>` 를 달았다 -- 판정은 "그 메시지" 라 실패.
  자식 `claude -p` 가 부모 세션의 서명 지시를 물려받은 흔적이다
- **MBA T2 1 회**: 도구가 켜진 컴파일 호출이 번역하지 않고 5 턴 동안 직접 실행했다(122k). **도구를 끈 BARE 는 이 실패가 없다** -- 컴파일 호출에는 도구를 주지 말아야 한다

### 이 실험이 **못** 보인 것
- **TOOL 팔은 강한 기준선이 못 됐다** -- 6 회 모두 walp MCP 도구를 한 번도 안 쓰고 Bash 로 했다. "사건 때만 LLM" 기준선은 아직 없다
- 과제는 MBA 의 닫힌 연산 집합 안에서 골랐다(사소한 설명 5). 일반 에이전트 대비 주장이 아니다
- haiku 하나 · 3 회 · 과제 다섯. 관문의 거절 효과는 재지 않았다(사전 9:1 로 늘 불렀다)
- BARE 는 머리를 바꾸고 도구를 없앴다 -- 그 몫이 "MBA 구조" 덕인지 "작은 머리로 부른 것" 덕인지는 이 표로 갈리지 않는다.
  같은 작은 머리로 LOOP 를 돌리는 팔(LOOP-bare)이 있어야 가른다

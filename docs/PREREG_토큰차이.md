# 사전등록 — 토큰 차이 실측 (V1)

**수를 보기 전에 커밋한다.** 하니스: `bench/token_ab.py`. 원자료: `bench/results/<실행ID>/runs.jsonl`.

## 물음

같은 과제를 (a) LLM 이 루프를 도는 방식과 (b) MBA(LLM 은 관문을 지난 컴파일 한 번, 나머지는 토큰 0 실행)로
돌렸을 때, **과제당 LLM 토큰(실패 포함)** 이 얼마나 다른가. 성공은 나빠지지 않는가.

## 0단계 — 계기부터 (이것이 서야 비교를 말한다)

모든 `claude -p` 호출마다 토큰을 **두 길** 로 센다.
1. 결과 JSON 의 `usage`(입력 · 캐시 만들기 · 캐시 읽기 · 출력)
2. 그 세션의 추적 파일(`~/.claude/projects/**/<session_id>.jsonl`)의 assistant 줄 usage 합(같은 message id 는 마지막 줄 하나)

**규칙:** 호출마다 네 종류 합의 차가 5% 이하. 하나라도 넘으면 비교를 보고하지 않고 그 까닭부터 적는다.
추가로 추적에 `Stop hook feedback` 이 있으면 적는다(이 컨테이너의 stop 훅이 턴을 늘렸는지).

## 팔

| 팔 | 무엇 |
|---|---|
| **LOOP** | `claude -p` 가 기본 도구(Bash 등)로 과제를 끝까지 한다. 기준선 |
| **TOOL** | LOOP + walp MCP 도구(`walp_wait` · `walp_publish`). "사건 때만 LLM" 에 가장 가까운 강한 기준선. T1 · T2 만 |
| **MBA** | 결정적 파서 → (못 하면) 관문 → `claude -p` 컴파일 **한 번**(LOOP 와 같은 깃발) → 닫힌 연산 집합을 토큰 0 으로 실행. 같은 질문 · 같은 상태는 캐시 |
| **MBA-bare** | MBA 와 같되 컴파일 호출에 `--tools ""`. 고정 머리(P) 몫을 따로 보려고 |

모두 `--model claude-haiku-4-5-20251001`, `--strict-mcp-config`(TOOL 은 walp 만), 권한 우회, 새 임시 디렉터리.

## 과제 (결정적 성공 판정)

| # | 과제 | 성공 |
|---|---|---|
| T1 기다리기 | 30초짜리 백그라운드 작업(PID 제공)이 끝나기를 기다려 로그 마지막 줄을 답 | 답에 `DONE 42` |
| T2 발행 | 새 파일 커밋 → 검사 → 로컬 bare 원격 main 으로 밀기 | 원격 main 에 그 파일 · 그 메시지 |
| T3 같은 질문 두 번 | "HEAD 커밋 제목이 뭐야?" 를 상태를 안 바꾸고 두 번(LOOP 는 같은 세션 `--resume`) | 두 답 모두 제목 포함 |
| T4 임무(어휘 안) | "연기 속에서 파란 물체를 찾아" → 기호 임무 | GOAL=SEARCH · TARGET=BLUE_OBJECT · ENV=SMOKE |
| T5 임무(어휘 밖) | "빨간 거 찾아봐" → 기호 임무 | GOAL=SEARCH · TARGET=RED_OBJECT |

과제 × 팔마다 **3 회**, 회차 안에서 팔 순서를 돌린다(캐시 데움 쏠림을 줄이려고).

## 관문 설정 (이 실험의 값 — D-R1 이 정해지기 전 임시)

컴파일 · 의도 자리의 사전 (9, 1) → p = 0.9 > θ 0.8. 그래서 관문은 이 실험에서 늘 부른다. **관문의 거절 효과는 이 실험이 재지 않는다.**

## 보고

과제 × 팔: 성공 수, LLM 호출 수, 토큰 네 종류 평균과 범위, 비용. MBA/LOOP · MBA/TOOL 비. 한 수로 합치지 않는다.

## 사소한 설명 — 재서 죽일 것

1. **MBA 가 0 인 것은 LLM 이 필요 없는 과제라서** — T4 는 정의상 그렇다(어휘 안). T4 는 "결정적 파서의 몫" 으로만 읽는다
2. **줄어든 것이 호출 수(N)가 아니라 머리(P)** — 호출당 토큰과 호출 수를 따로 적고, MBA 와 MBA-bare 를 맞댄다
3. **캐시 순서** — 캐시 만들기 · 읽기를 따로 적는다. 팔 순서를 돌린다
4. **LOOP 가 실패해 재시도로 부풀었다** — 성공 수와 턴 수를 같이 적는다
5. **MBA 는 닫힌 연산 집합 밖의 과제를 못 한다** — 이 과제들은 그 집합 안에서 골랐다. 일반 에이전트 대비 주장이 아니다

## 무효화

- 0단계 계기 대조가 5% 를 넘으면 전부
- MBA 의 성공이 LOOP 보다 적은 과제는 그 과제의 차이를 주장하지 않는다
- 차이가 런 간 범위 안이면 "차이 없음"

## 파일럿 (본 측정에서 뺀다) -- 하니스 결함 둘을 고쳤다

`bench/results/pilot`, T5 · T3 × LOOP · MBA · BARE 1 회.
1. **계기 대조가 70,000% 어긋났다.** 자식 `claude -p` 가 부모 세션 ID(`CLAUDE_CODE_SESSION_ID`)를 물려받아 추적 합이 부모
   세션 전체를 읽었다. 자식 환경에서 그 변수를 지우고 `--session-id` 를 새로 준다. (walp 그림자 실험의 "다섯 세션이 이 세션의
   session_id 를 물려받았다" 와 같은 원인)
2. **MBA 컴파일 호출이 번역하지 않고 직접 답했다**(T3: "git 저장소가 아닙니다"). 컴파일 프롬프트에 "실행하거나 답하지 말고
   옮겨라" 와 `<요청>` 경계를 넣었다. 파일럿의 수치는 보고하지 않는다.
3. **(파일럿 2)** 계기 대조는 섰다(7 호출, 최대 차 0.00%, stop 훅 흔적 0). 그러나 고친 프롬프트로도 T3 컴파일이 실패했다 --
   MBA 는 환경을 설명했고 BARE 는 형식 지시를 거절했다. 컴파일러 역할을 **시스템 프롬프트** 로 옮겼다:
   MBA = `--append-system-prompt`(기본 머리 유지), BARE = `--system-prompt`(머리 교체). BARE 의 머리가 바뀌므로 MBA 와 BARE 의 차가
   곧 P 의 몫이다.
4. **(파일럿 3)** T3 는 MBA · BARE 모두 섰다(첫 질문 컴파일 1 회, 두 번째는 캐시). T5 BARE 가 실패했다 -- 임무 과제에도 연산
   컴파일러 역할이 걸렸다. T4 · T5 에는 임무 컴파일러 역할(`MISSION_ROLE`)을 준다. 여기서 하니스를 얼린다.

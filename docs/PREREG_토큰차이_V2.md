## 팔 — 구조 3 × 머리 2

| 구조 \ 머리 | 기본 머리(Claude Code 시스템 프롬프트 + 도구 정의) | 작은 머리(지시 한 장, ~200자) |

| **MBA**(컴파일 한 번 + 토큰 0 실행 + 캐시) | MBA | BARE |

(V1 TOOL 팔은 6 회 모두 안 불러 기준선이 못 됐다).

## 판정 바뀐 것 하나
T2 성공: 원격 main 의 제목이 `add feature` 로 **시작** 하면 성공(V1 은 정확히 같음). V1 에서 자식이 서명 줄을 제목 줄에 붙여
실패로 셌던 회차 때문 -- 수를 보기 전에 바꾼다.

## 가르는 법

과제마다 평균 토큰 T(팔). 로그 비는 더해진다:

    log(LOOP/BARE) = log(LOOP/LOOPB)   [머리 몫, 루프에서]  + log(LOOPB/BARE) [구조 몫, 작은 머리에서]
                   = log(LOOP/MBA)     [구조 몫, 기본 머리] + log(MBA/BARE)   [머리 몫, MBA 에서]

두 길을 **둘 다** 적는다. 두 길의 머리 몫이 다르면 그 차가 상호작용이다(머리를 줄인 효과가 구조에 따라 다르다).
강한 기준선 대비 구조 몫: `EVENT/MBA`(기본 머리) · `EVENTB/BARE`(작은 머리).

## 가설 · 판정

- **H-head**: 같은 구조 안에서 작은 머리가 토큰을 줄인다(LOOP>LOOPB, MBA>BARE, EVENT>EVENTB)
- **H-struct**: 같은 머리 안에서 MBA 구조가 루프보다 적다(LOOP>MBA, LOOPB>BARE)
- **H-strong**: 같은 머리 안에서 MBA 구조가 사건 도구 기준선보다 적다(EVENT>MBA, EVENTB>BARE) -- T1 · T2
- 각 비교는 **범위가 겹치지 않고** 적은 쪽의 성공이 많은 쪽보다 나쁘지 않을 때만 "섰다". 겹치면 "차이 없음"
- 과제마다 따로. 한 수로 합치지 않는다

## 사소한 설명 — 재서 죽일 것
1. 작은 머리의 이득이 **지시문 내용**(예: "확인을 묻지 마라") 때문에 성공이 바뀐 것 -- 성공 수를 팔마다 적는다. 성공이 다르면
   토큰 비교를 그 쌍에서 주장하지 않는다
2. EVENT 의 이득이 **내장 도구 정의를 뺀 것**(머리가 작아짐) -- EVENT 와 LOOP 의 캐시 토큰을 따로 적는다
3. T4 의 0 은 정의상(V1 과 같다)
4. 캐시 데움 -- 팔 순서를 회차마다 돌린다(V1 과 같다)

## 무효화
- 계기 대조 5% 초과 -> 전부
- 한 쌍에서 성공 수가 다르면 그 쌍의 토큰 비교는 주장하지 않는다

### 판정 (사전등록 규칙: 범위가 안 겹치고 성공이 같을 때만 "섰다")

**H-head — 섰다.** 같은 구조 안에서 머리를 줄이면:
루프 4.8~6.5배(T1~T5 모두 섰다) · 사건 도구 2.1~2.5배(T1 · T2 섰다) · MBA 14~24배(T1 · T3 · T5 섰다, T2 는 성공이 달라 주장 안 함).

**H-struct (기본 머리, 깨끗한 쌍) — T3 만 섰다.**
- T3: LOOP/MBA = **4.0배** 섰다(같은 질문을 두 번 -- 루프는 두 번째에 이력까지 다시 읽고, MBA 는 캐시)
- T5: 0.985 — 차이 없음(둘 다 한 호출)
- T1 2.0배 · T2 5.1배 — **성공이 달라 주장하지 않는다**(T1 LOOP 1/3 vs MBA 3/3, T2 LOOP 3/3 vs MBA 2/3)

**H-strong (강한 기준선, 기본 머리) — 서지 않았다.**
EVENT/MBA: T1 **0.97** · T2 **1.32**, 둘 다 성공이 달라 주장 안 함. 숫자로도 **사건 도구를 가진 에이전트와 MBA 구조의 토큰 차는
거의 없다.** V1 에서 본 MBA/LOOP 0.27~0.49 의 대부분은 "LLM 이 폴링 · 여러 턴을 도는 것" 대 "한 번" 의 차였고, 그 차는
사건 도구(walp_wait · walp_publish)만 줘도 대부분 사라진다.

### 결론 — 줄어든 몫은 대부분 머리 덕이다
1. **머리(호출마다 다시 실리는 고정 머리)가 가장 큰 지렛대다.** 전체 감소의 62~100% (기본 머리 길).
2. **구조(MBA: 한 번 컴파일 · 토큰 0 실행 · 캐시)의 몫은 루프 대비 0~38%**, 그중 규칙대로 선 것은 T3(같은 질문 반복, 4.0배) 하나.
3. **강한 기준선(사건 도구) 대비 MBA 구조의 이득은 이 실험에서 보이지 않았다**(0.97 · 1.32, 주장 불가).
4. 가장 싼 조합은 **MBA 구조 + 도구 없는 작은 머리(BARE)** — 모든 과제에서 가장 적고, V1 · V2 합쳐 30/30 성공. 그러나 이 이점의
   대부분은 머리에서 왔다.

### 실패와 그 까닭 (추적에서 직접 봄)
- LOOP · LOOPB T1: 남의 PID 에 `wait` -- 기다리지 않고 `step1/2` 를 답했다(V1 과 같은 실패)
- EVENT T1 1 회: `walp_wait` 가 로그 끝 줄을 돌려줬는데 관계없는 `walp_run` 을 세 번 부르고 "읽을 권한이 없다" 로 끝남
- EVENTB T1 1 회: 읽지 않은 로그 끝 줄을 **지어냈다**(`SUCCEEDED`)
- MBA T2 1 회: 컴파일 호출이 번역하지 않고 "git 저장소가 아닙니다" 로 답함(V1 에도 같은 꼴). **BARE 는 V1 · V2 에서 이 실패가 0** --
  컴파일 호출은 도구 없이 작은 머리로 해야 한다

### 이 실험이 못 보인 것
- 작은 머리 쌍을 맞추지 못했다(LOOPB 에 Bash 정의). 맞추려면 BARE 에도 같은 Bash 정의를 실어 부르는 팔이 필요하다
- 과제 다섯 · haiku 하나 · 3 회. 과제는 MBA 의 닫힌 연산 집합 안에서 골랐다
- 사건 도구 기준선은 walp 도구 둘뿐이다. T3 같은 "같은 질문 반복" 에는 사건 도구 기준선이 없다
